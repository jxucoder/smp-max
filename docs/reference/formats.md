# Data formats and conventions

## Instances and matchings

Participants are labeled `0` through `n-1`. A matching `mu` maps man `m`
to woman `mu[m]`; its inverse maps a woman to her partner.

| Representation | Meaning | Used by |
|---|---|---|
| Best-first preference list `mpref[m]` | Partner labels in preference order | [stable_matchings.py](../../tools/stable_matchings.py), witness JSON |
| Zero-based rank table `mrank[m][w]` | Position of woman `w` in man `m`'s list; 0 is best | Lean, schedule encoding, rotation-poset counter |
| Zero-based rank table `wrank[w][m]` | Position of man `m` in woman `w`'s list | Same; rows are indexed by women |
| Original f(7) paired table entry `(a,b)` at row `m`, column `w` | One-based male rank `a`, one-based female rank `b` | [Historical witness text](../../results/f7/witnesses-85.txt) |

Every preference row must be a permutation. The original paired tables
must be transposed when constructing women's rank rows; subtract one
from ranks before passing them to the zero-based counters.

## Witness JSON, version 1

Each file has `format_version: 1`, a `preference_format` description, and
a nonempty `witnesses` list. Each witness records `id`, `order`,
`expected_count`, `men_preferences`, `women_preferences`, and `source`.
Optional `schedule` stores a list of cyclic steps. Preference lists are
best-first with zero-based partner labels. The verifier checks the data,
rather than trusting the recorded expected count.

## Schedules and cubes

A step `[m0, m1, ..., mr]` gives each listed man the current partner of
the next man, wrapping around. A size-2 step is a swap. All schedules
start from the identity matching. No participant may revisit a partner.

A campaign cube ID such as `0,1;2,3` fixes two steps. `0,1;stop` also
requires termination after the first step; `stop` is the empty schedule.
Cycle tuples use their minimum label first. First-appearance normalization
and the legality filter define the canonical campaign prefixes.

Cube IDs and the `c_<tag>.cnf` naming generated by `cube_tag` are historical
identifiers. Do not replace them with cosmetic new names inside journals.

## CNFs and certificates

DIMACS begins with `p cnf VARIABLES CLAUSES`, followed by integer literals
and a terminating `0` per clause. Exact variable and clause ordering are
part of the formula identity used by the campaign.

The order-5 upper-bound cubes retain `cubeL000.cnf` through `cubeL119.cnf`.
The exporter also emits 120 threshold-16 positive-control formulas and
`perms120.txt`. Direct PySAT CNFs use a different encoding from these
Lean selector formulas and from the order-6 schedule encoding.

DRAT/LRAT files are solver proof artifacts. A SHA-256 in a journal identifies
the bytes that were checked; without those bytes it is not a proof check.
See [campaign records](campaign.md) and the [artifact manifest](../../results/manifest.json).
